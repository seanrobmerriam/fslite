# Release 0.1.1 Design

## Purpose

Publish the workspace-relative CLI path behavior merged in PR #2 as a patch
release that existing `cargo install fslite` users can receive. Version
`0.1.0` of both affected packages is already published and cannot be
replaced, so the next release is `0.1.1`.

## Release Scope

Only packages whose published artifacts changed are versioned:

- `fslite-command`: `0.1.0` to `0.1.1`, because its parser and help metadata
  now accept and document workspace-root-relative paths and glob patterns.
- `fslite`: `0.1.0` to `0.1.1`, because its installed CLI help, README-facing
  workflow, and end-to-end behavior changed.

The `fslite` manifest raises its minimum `fslite-command` dependency from
`0.1.0` to `0.1.1`. This prevents Cargo from installing the new CLI against
an older command parser that still rejects relative paths.

`fslite-core`, `fslite-sqlite`, `fslite-server`, and `fslite-conformance`
remain at `0.1.0`; their published code and public contracts did not change.

## Files and Generated State

The release changes:

- `crates/fslite-command/Cargo.toml`;
- `crates/fslite-cli/Cargo.toml`; and
- the affected workspace package entries in `Cargo.lock`.

No changelog is introduced because the repository does not currently have
one. The pull request body serves as the release summary and includes the
user-visible relative-path examples.

## Validation

Before opening the release pull request:

- verify Cargo metadata reports `fslite-command 0.1.1` and `fslite 0.1.1`;
- run formatting and Clippy with warnings denied;
- run the complete workspace test suite;
- run `cargo publish --dry-run -p fslite-command`;
- run `cargo publish --dry-run -p fslite` only after temporarily validating
  how Cargo resolves the not-yet-published `fslite-command 0.1.1` dependency,
  or defer this second dry-run until the dependency is published; and
- inspect package contents to ensure no local worktree or planning artifacts
  enter the crates.

The release PR does not publish or tag anything. Actual crates.io publishing
remains a separate explicitly authorized operation after merge.

## Publish Order After Merge

1. Publish `fslite-command 0.1.1`.
2. Wait until crates.io resolves that exact version.
3. Dry-run and publish `fslite 0.1.1`.
4. Verify with `cargo install fslite --version 0.1.1 --force` and a relative
   `mkdir`/`write`/`cat` workflow.

## Acceptance Criteria

- The release PR contains only version/dependency/lockfile changes plus its
  committed design and implementation plan.
- Only `fslite-command` and `fslite` report version `0.1.1`.
- `fslite 0.1.1` requires `fslite-command 0.1.1`.
- All local checks and the publishable `fslite-command` dry-run pass.
- No crates.io publish, Git tag, or GitHub release is created by this task.
